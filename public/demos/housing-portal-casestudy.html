Case Study

Housing Portal and two-way Zoho CRM integration

A client portal built onto an existing marketing website, kept in step with the business's CRM in both directions.

Sole developer and integration engineer TypeScript React tRPC Drizzle ORM MySQL Express Railway Zoho CRM v8

What it is

A UK property group places residential property with care providers. Their whole business already lived in Zoho CRM: properties, the companies they deal with, and the deals that track each placement from first viewing to contract.

What they did not have was a way for their clients to see any of it. Property owners emailed details in. Care providers asked what was available and waited for someone to reply. Everything that happened outside Zoho had to be typed back into Zoho by hand.

I built them a portal, attached to their existing website, where property owners submit and track their properties and care providers browse what is available, shortlist it, ask questions and request viewings. Behind it, a two-way synchronisation keeps the portal and Zoho in agreement without anyone retyping anything.

The hard part was never the screens. It was the synchronisation.

What I built

Access and accounts

Request access from the public site, admin approval, time-limited invitation links, activation. Two client types with different permissions. Every approval, rejection and re-invitation is recorded, and each state says plainly where it stands.

The property register

Owners submit a property with documents and photographs. Admins review, complete and publish it. Compliance paperwork is tracked per property, and commercial figures stay hidden unless a property is explicitly set to show them.

Matching and notifications

Clients save what they are looking for. When a property is published, matching clients are found and emailed automatically, rather than an administrator remembering to press a button.

Enquiries

Shortlisting, questions and viewing requests, each threaded so the whole exchange is kept, with the client emailed whenever somebody replies.

Deal automation

Each property gets one deal in the CRM's own pipeline, at the right stage, owned by the right person, linked to the property and the landlord's account. Interested providers are collected onto that deal. Closing the deal takes the property off the portal by itself.

Invoicing

An invoice is raised in the accounting system as soon as a billing template is chosen on a deal, without the team leaving the CRM.

The integration work, and what it actually takes

Two-way sync is easy to describe and unforgiving to build. Most of the engineering below came from problems that only appear against real data.

Never create a second copy of something that already exists

The first version created a CRM property for every portal property without checking. Most already existed, so real records ended up with a short-named duplicate beside them.

I replaced it with address matching that compares the part which identifies a building: flat number, house number including ranges like 49-55 and 292/294, and the first word of the street. Postcode and street type are only compared when both records carry one, because one side often does not. An exact match links to the existing record, an unsure match is referred to a human rather than guessed, and no match creates a new record.

12 duplicate pairs merged, 264 records down to 252, no duplicate addresses left

Never overwrite better data with worse

The portal knows a short version of an address and of a company name. The CRM usually holds the fuller, legal one. Sending those fields on every update quietly degraded the better record, so names are now sent when creating a record and never when updating one.

Fail loudly, and keep the reason

A rejected write used to be stored as "HTTP 400" with the API's actual explanation discarded, which turned a one minute diagnosis into a five day investigation. Every rejection now keeps the response body, redacted of secrets, and surfaces it in the admin screens and the alerts.

Respect the target system's rules

Real constraints found and handled: the API rejects a request asking for more than fifty fields, so the field list is capped and guarded by a test. Deals cannot be created through the upsert endpoint because that module has no unique field, so they are created outright. A layout can make a field mandatory even when the field metadata does not say so, so the missing value is reported by name instead of sending a request that can only be refused.

Never silently delete

Writing a multi-select field sends the entire list, so a partial read would quietly drop everyone missing from it. That write refuses to run on an incomplete read, and every write is read back and rejected if anybody who was there has gone.

Handle conflict honestly

When both sides change the same record between syncs, neither is overwritten. The record is held for review and an administrator can release it from the dashboard, taking the CRM's version.

Do not set off other people's automations

Background synchronisation suppresses the CRM's workflow rules. A record moved backwards by a sync should not re-trigger emails and assignments meant for a human doing it deliberately.

Reliability

  • Events are written to an outbox in the same transaction as the change that caused them, so an outage can never lose one.
  • Deliveries retry with backoff, and a rejection caused by bad data is not retried forever.
  • Receipts make every operation idempotent, so a replay cannot duplicate work.
  • A reconciliation runs every fifteen minutes: it drains both delivery queues, reads deal stages back, and reports failures to email and a monitoring channel on the first failure rather than every cycle.
  • The application refuses to start if the database is missing a migration the build expects, and applies its own migrations where the database is reachable.
  • Traffic stays on the previous version until the new one answers a health check. A deploy that cannot run correctly fails as a deploy, instead of taking the site down.

What it changed

Clients can see the stock, register interest and get an answer without an email thread. The team works in the CRM they already know and the portal follows. Records that used to be typed twice are now typed once, and the duplicates that had built up before the portal existed were found and merged as part of the work.

The part I am most pleased with is not a feature. It is that the integration refuses to guess. Where the data is ambiguous it says so and asks a person, rather than picking an answer and quietly corrupting a record that somebody relies on.
