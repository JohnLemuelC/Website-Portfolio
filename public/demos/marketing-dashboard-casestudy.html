A multi-channel marketing analytics platform for a 187-account agency

I designed and built the data pipeline, warehouse model and web application that replaced a sprawl of Google Sheets — unifying five ad platforms and three SEO data sources into a single warehouse, and giving both the agency and its clients a live view of performance, budget pacing and wasted spend.

The problem

Reporting lived in spreadsheets that nobody trusted

Performance data for every client sat in a chain of manually-refreshed Google Sheets. Each platform had its own tab, its own owner and its own definition of “spend”. Month-end reporting took days, numbers disagreed between documents, and no client could answer a question without emailing someone.

Fragmented

Five platforms, five truths

Search, social, display and SEO each reported separately, with no common account key to join them on.

Manual

Humans as the ETL

Refreshes depended on someone remembering. A missed run silently produced a report full of stale numbers.

Closed

No client self-service

Every client question became an internal ticket, because there was no safe way to expose one client's data without exposing others.

Architecture

Batch ETL into a warehouse, with a thin read-only app on top

The core design decision: the web app never calls an ad platform. Every figure it renders was written to the warehouse earlier by a scheduled job. That keeps page loads fast and predictable, makes the app resilient to platform API outages, and means a rate limit can never break a client's dashboard.

Engineering highlights

Four problems worth solving properly

The interesting work wasn't the charts — it was making the platform safe to expose, cheap to run, and honest about its own health.

The problem

Letting clients query their own data — without trusting a prompt

The platform includes a natural-language query interface: a client asks a question in English and a language model writes the SQL. The obvious risk is a model that writes SQL reaching another client's rows.

Prompt instructions are not a security boundary. So enforcement happens in SQL instead. Every client query is rewritten before execution — a shadowing common table expression is injected for each referenced view, pre-filtered to that client's accounts, so the view name can only ever resolve to the filtered set. The generated SQL is additionally validated to reject qualified names and backticks that could escape the rewrite.

The result: no output the model can produce reaches another tenant's data, regardless of what it writes or what a user talks it into.

The problem

Giving every client an AI analyst at no marginal cost

Clients wanted conversational access to their data. Running that through the agency's own model API would mean paying per token for every client question — a cost that scales with adoption and is impossible to forecast.

Instead I implemented a standards-based connector so clients attach the platform to their own AI subscription. The server only ever answers structured tool calls with scoped data; it never invokes a paid model itself. Each client login gets its own revocable token, and the same SQL-level scoping applies.

Adoption now costs the agency nothing per query, and the analytical capability improves for free as the client's own AI provider improves.

The problem

Making re-runs safe across ten years of daily data

Ad platforms restate history: conversions attribute late, spend gets adjusted days after the fact. A pipeline that simply appends produces duplicates; one that deletes and rewrites risks losing data if it fails midway.

Every fact table carries a pull timestamp stamped once per run, and every read takes the most recent row per key. Re-running any window is therefore idempotent — a backfill, a gap-fill and the nightly job can overlap freely without producing a single double-counted metric.

Deep history is loaded in chunks by a separate mode, so a decade of backfill never blocks the nightly refresh.

The problem

A pipeline that reports “healthy” when it has stopped

The original health check recorded success whenever an API call didn't throw. A paused account and a silently broken integration produced identical green ticks — one source went 218 days without data while still reporting healthy.

I replaced it with durable run history in a database rather than ephemeral container logs, recording every outcome — clean exit, non-zero exit, timeout and crash — plus a per-source staleness threshold derived from its expected cadence. Anything overdue for its own schedule raises an alert.

The monitoring is deliberately best-effort and non-blocking: if the telemetry store is unreachable the job still runs and logs a warning. A monitoring outage must never become a pipeline outage.

Integration work

Meeting data where it already lives

One client group tracked budgets in a spreadsheet their team owned and could not share outside their organisation — a hard constraint, not a preference. Rather than ask them to change process, I inverted the direction of the integration.

  • A script running inside their own document reads the figures and pushes them out, so no external access to the file is ever required.
  • It authenticates to a purpose-built endpoint with a shared secret, and every incoming account is checked against a fixed allowlist — a leaked secret could still only ever move budgets for that one client group.
  • Human-authored fields are read back and passed through untouched, so an automated sync can never overwrite a note somebody typed.
  • It runs on a daily schedule and is fully idempotent.

Thirty client budgets across four channels now flow in automatically each morning, from a source the platform is not permitted to read.
